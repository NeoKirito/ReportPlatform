# ReportPlatform Controlled Field RC1 Deployment Guide

> **Scope.** This guide prepares a controlled Windows field pilot. It does not authorize use of patient data, production database writes, physical printing, network scanning, or a claim of historical-report compatibility. Complete the existing [field acceptance checklist](FIELD_ACCEPTANCE_CHECKLIST.md) for any field-only evidence.

## 1. Package and configuration preparation

Build the release assets with `scripts\\Build-Release.ps1 -Clean`, then create the reproducible field package with `scripts\\New-FieldRc1Package.ps1 -ShortSha <short-sha>`. The result is `release\\ReportPlatform_RC1_<short-sha>\\` and `release\\ReportPlatform_RC1_<short-sha>_win-x64.zip`. Keep `report-api/`, `print-agent/`, `scripts/`, `docs/`, and `config-templates/` together. The packer explicitly excludes `appsettings.Production.json`, AgentId, `.runtime`, SQLite, PDF/FRX, browser evidence and build intermediates. Copy the API and agent templates to the appropriate published directories as `appsettings.Production.json`, then replace placeholders through the approved local configuration channel. Do not place a production configuration, connection string, token, AgentId, printer name, patient file, or runtime database into source control or the RC ZIP.

The API is framework-dependent for `win-x64`; install the matching .NET runtime before starting it. The PrintAgent is a `win-x64` self-contained deployment. Production requires HTTPS, `PrintAgentSecurity:RegistrationToken`, `InternalApiSecurity:AccessToken`, and `ArtifactAccess:SigningKey`. The controlled pilot begins with `PrintBackend:Mode = DryRun`.

## 2. Execute preflight before starting services

Run an elevated PowerShell only when the intended service account and package directory require it. The script does not install software, print, alter production configuration, change Windows security policy, touch a database, or write AgentId. It creates and removes only temporary probes and synthetic fixtures.

```powershell
.\scripts\Test-FieldPreflight.ps1 `
  -Mode Production `
  -ApiDirectory .\report-api `
  -AgentDirectory .\print-agent
```

Use `-Json` for deployment automation. Its output contains states and safe paths only; it never emits secret values, connection strings, patient data, or printer configuration values. A production result must be `FINAL: READY_FOR_DRY_RUN`. Resolve every `FAIL` before starting the API. `Legacy SQL` and `FastReport` remain `NOT_CHECKED` unless the separately approved read-only test path is explicitly enabled.

## 3. Start and probe the Report API

Start the Report API using the controlled production service definition. Confirm the configured HTTPS address and perform the approved health check:

```text
GET https://<REPORT_API_HOST>:<REPORT_API_PORT>/health
```

A health response only confirms service availability. It does not establish database compatibility, report visual equivalence, or printing readiness. Do not discover database hosts or retry credentials outside the approved deployment record.

## 4. Install and configure PrintAgent

Confirm that `PEIS.PrintAgent.exe` and its production configuration are in the intended agent directory. Configure a valid `StationId`, explicit logical `PrinterBindings`, HTTPS `ServerUrl`, and a non-empty registration token. Use the existing installer with the approved local values; no real values should be copied into this guide or command history exports.

```powershell
.\scripts\Install-PrintAgentAutoStart.ps1 `
  -AgentDirectory <AGENT_DIRECTORY> `
  -StationId <STATION_ID> `
  -ServerUrl https://<REPORT_API_HOST>:<REPORT_API_PORT> `
  -RegistrationToken <REGISTRATION_TOKEN> `
  -PrinterBindings @{ A4_GUIDE = '<A4_GUIDE_PRINTER>'; BARCODE = '<BARCODE_PRINTER>' }
```

The installer writes controlled local production configuration and installs a scheduled task. The stable AgentId is generated by the agent on first successful start under `%ProgramData%\PEIS\PrintAgent\agent-id.txt`; do not delete or manually replace it during upgrades. Check the API’s approved internal status endpoint and the agent log for a registered, online agent before any DryRun action.

## 5. Local DryRun gate

Keep `PrintBackend:Mode` set to `DryRun`. Run only a synthetic or approved non-patient business action. Verify that a job is persisted, dispatched, acknowledged by the agent and completed; restart the API, query the same job, and retry the same idempotency key. The expected outcome is a single logical JobId and no duplicate target. Record only non-sensitive metadata.

> **NO PHYSICAL PRINTING OCCURRED** during the DryRun gate. A DryRun completion is not evidence of A4 or barcode printer behavior.

## 6. Separate physical-printing field gate

Only after DryRun is accepted may the responsible field team authorize a separate physical-printing gate. That gate must validate A4 paper and margins, barcode device output and scan readability, Chinese fonts, watermarks, actual printer driver behavior, and fault handling for paper/queue conditions. These remain **FIELD_REQUIRED** until written field evidence is attached to the acceptance checklist.

## 7. Restart, cleanup and rollback sequence

For the controlled restart gate, restart the API and then the PrintAgent. Confirm that the persisted job remains queryable, the AgentId is unchanged, and cleanup only removes expired inactive artifacts. Do not perform cleanup on unmanaged patient artifacts as part of preflight.

To roll back, stop or disable the new API service and return the approved reverse-proxy or service route to the previous PEIS reporting service. Disable the `PEIS PrintAgent` scheduled task with `Uninstall-PrintAgentAutoStart.ps1`; it preserves AgentId and local state unless `-RemoveLocalState` is explicitly supplied. Do not remove printers, drivers, PEIS files, or database state. Record the decision and timestamps in item F-19 of the field acceptance checklist.

## 8. Remaining field-only evidence

The following states cannot be converted to PASS by this RC1 package: real A4 printing, real barcode printing and scanning, Chinese font and watermark visuals, all historical FRX files, old/new PDF manual equivalence, large real-report performance, onsite TLS/network behavior, and physical printer fault behavior. Use [PDF visual acceptance](PDF_VISUAL_ACCEPTANCE.md), [report compatibility matrix](REPORT_COMPATIBILITY_MATRIX.md), and [field acceptance checklist](FIELD_ACCEPTANCE_CHECKLIST.md) to collect that evidence in the approved environment.
